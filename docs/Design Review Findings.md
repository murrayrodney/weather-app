# Design Review Findings

Review of `Family Weather App Design Doc.md` by two adversarial reviewers (security; practicality/feasibility/cost/containers), Oct 2, 2026. Each item needs a decision before the per-component guides are written. Prices and third-party API details come from the reviewers' knowledge and should be checked before deciding.

## Security (highest priority)

- [x] **S1. Token checks must be strict.** The API must check more than the token's signature, or it could accept Supabase's public "anon" key as a login. Allow only the expected signing method, check audience, issuer, expiry and user ID, and add tests that try the anon key, expired tokens and unsigned tokens.
- [x] **S2. Decide where the login token lives.** Keeping it in the browser exposes it to malicious scripts, while keeping it in a cookie needs protection against cross-site requests. Pick one now, because it changes the frontend, the API and the security headers. **Decision:** the browser holds the token via Supabase's library and sends it to the API on each request, with a strict content security policy, no third-party scripts, pinned npm packages, and a per-request check that the user is active and their Supabase session still exists (through `app_auth` database functions, proposal 03). Revisit (move to an API-owned cookie session) if users grow beyond family or outside scripts or user content are added.
- [x] **S3. The Fly API is public even with the Netlify proxy.** Anyone can call the `fly.dev` address directly and fake their IP address. Require login on every route, rate-limit per user rather than per IP, and optionally have Netlify sign proxied requests so the API rejects everything else.
- [x] **S4. "Invite-only" is not the Supabase default.** Anyone holding the public key can sign up or request a magic link unless sign-ups are switched off in Supabase. Turn off open and anonymous sign-up, and have the API also check that the user is on the app's own allow-list.
- [x] **S5. One binary means the API can read every AWN key.** The doc says only the poller reads credentials, but the API and poller share a process, a database login and the encryption key. Give them separate database logins (the API can't read `credentials`) and ideally run them as two processes from the same image. **Decision:** separate database logins, and the API and poller run as separate Fly apps (four apps in all: `famweather-api`, `famweather-poller`, `famweather-admin`, `famweather-backup`; see P3 and proposal 02); only the poller app has the private decryption key. Resolved via HPKE; see proposal 01.
- [x] **S6. Hide tables from Supabase's built-in REST API.** Relying on "row-level security with no rules" leaves gaps: one forgotten table, view or function becomes readable with the public key. Put app tables in a private schema (or turn the REST API off) and add a check in CI. **Decision:** app tables live in a private schema hidden from the REST API (or the REST API is turned off), with a CI check.
- [x] **S7. AWN keys can leak through error messages.** AWN puts keys in the URL, and the Rust HTTP library prints full URLs in errors, traces and crash messages; a key passed to the CLI also lands in shell history. Strip URLs from errors, read the CLI key from a prompt, and add a test that checks logs for the key.
- [x] **S8. Spell out the encryption details.** Use a fresh random value for every encryption, tie each encrypted key to its row so it can't be swapped, and store a key version so the master key can be rotated. Also decide what threat this protects against, since the master key and database password sit side by side in Fly secrets. **Decision:** HPKE public-key encryption with the row id and owner id as bound data and a key version column; the API holds only the public key. Resolved via HPKE; see proposal 01.
- [x] **S9. The "check AWN key" feature can be abused.** A user could use it to test stolen keys or to use up the shared rate limit and stall polling. Rate-limit it per user, return only valid/invalid, and never accept a URL or host from the user.
- [x] **S10. Every endpoint must run the access check.** One endpoint that skips `can_view` lets a user read others' data by changing an ID, and station coordinates reveal home locations. Build the check into the request handling so it can't be forgotten, use random IDs, round coordinates, and test each endpoint as a stranger, a pending follower and a revoked follower.
- [x] **S11. Removed users stay logged in for up to an hour.** Deleting someone in Supabase doesn't cancel tokens already issued. Check an "active" flag on every request (same allow-list as S4).
- [x] **S12. Lock down the database connection.** Use least-privilege logins with verified encrypted connections, never the `postgres` admin login. Don't let a developer read-only login see credentials or auth data, and avoid copying family data onto laptops.
- [x] **S13. Backups contain sensitive data.** A full dump holds encrypted AWN keys and possibly emails and login tokens. Encrypt dumps before upload, store them somewhere separate from the master key, set retention, and test a restore.
- [x] **S14. Protect the build and deploy pipeline.** Use deploy tokens limited to their own Fly app (one each for the API, poller and backup apps), pin GitHub Actions versions, and remember that any `PUBLIC_` variable ships to the browser. Netlify preview deploys are public and use production settings by default, so turn them off or point them at a separate project. **Decision (revised; web gating per proposal 04):** Netlify publishes only a `production` branch that the approved deploy workflow fast-forwards after the API deploy (no Netlify token in GitHub). Keep deploy previews for pull requests (useful for review); branch deploys off; skip Dependabot preview builds; add one preview callback pattern to Supabase's redirect list; previews use the production backend, so only sign in on previews of changes you've read.
- [x] **S15. Add browser security headers.** The doc doesn't mention a content security policy, HTTPS enforcement or anti-framing headers. Set them in Netlify or SvelteKit config, which matters most if tokens live in the browser.
- [x] **S16. Add an audit trail and a delete/recovery story (lower priority).** Log logins, follow decisions and credential changes, and define what deleting an account removes. Require two-factor login on the Supabase, Fly and Netlify dashboards.

## Practicality and architecture

- [x] **P1. Three hosting vendors is a lot for 3 stations and ~5 users.** Each adds its own deploys, secrets, limits and failure modes, and the Netlify proxy exists only to join two of them. Decide between the current mix, "Fly + Supabase only", or one small server running Docker Compose (see C1). **Decision:** keep the current mix: Netlify serves static files and proxies `/api/*`, Fly runs the Rust image, and Supabase provides Postgres and login.
- [x] **P2. Server-side rendering probably isn't needed.** The app is login-only and gets all its data from the Rust API, so a static single-page build is simpler and runs anywhere. Choosing it also largely settles S2 and the container question (D3). **Decision:** static single-page app (static adapter, server rendering off); components fetch data from `/api/*` in the browser.
- [x] **P3. Fly's defaults break the built-in poller.** Fly starts two machines (double polling) and stops idle ones (missed polls lost forever). Run exactly one always-on poller and add a database lock so two can never run at once. **Decision (revised by proposal 02):** run the API and the poller as separate Fly apps (`famweather-api`, `famweather-poller`, plus `famweather-admin` and `famweather-backup`) from the same codebase and image, with exactly one machine each (no high-availability pair), because Fly secrets are app-wide. The poller is always on, and every poller job takes a database lock so a second copy can never write at the same time.
- [x] **P4. Nothing defines how the schedule runs or alerts.** Timers inside the app miss runs during every deploy, and no one is told when polling stops. Have each job catch up from its last success on start, log runs to a table, and ping a free "dead man's switch" service that emails when runs stop. **Decision:** the poller is fully independent of the API. Each job catches up from its last successful run when the poller starts, logs every run to a `job_runs` table, and pings a free alerting service (e.g. healthchecks.io) that emails when expected runs stop arriving.
- [x] **P5. The follow/approval system is heavy for one family.** Pending, approved, declined and revoked states mean real UI and logic for people who will all see everything anyway. Consider one shared "family" group for v1, keeping `can_view` as the single check so follows can be added later. **Decision:** keep the full follow/approval system so new people can join without a rewrite. For now, seed every family member as mutually approved; `can_view` stays the single access check.
- [x] **P6. Trim version 1.** The guided connect flow serves about three one-time setups, so the CLI may be enough, and forecast-vs-gauge depends on data that arrives after v1. Consider v1 = ingestion plus year-to-date rain and GDD charts, deferring percentile bands, the connect UI and forecast comparison. **Decision:** no trimming. The guided connect flow and percentile bands are both required in v1; the CLI is only a stopgap for setting up the first stations. Forecast-vs-gauge stays where the design doc already puts it, after v1.
- [x] **P7. Add an "Operations" section.** Testing with recorded API responses, log retention, restore drills, key rotation and where the attribution credit appears are all missing. Cover these before the component guides. **Decision:** add an Operations section to the design doc (testing with recorded responses, logging, restore drills, key rotation, attribution) before writing the component guides.

## Data feasibility

- [x] **F1. Snapshotting every forecast run is large.** Hourly ensemble data for 3 locations is roughly 20 million rows (2–4 GB) a year, which blows past free-tier limits. Store daily or 6-hourly totals and probabilities instead (about 100 MB a year), and fetch when a new run is published rather than on a fixed clock. **Decision:** store 6-hourly aggregates, and fetch and write only when a new model run is published. **Superseded Oct 7, 2026 (proposal 06, option A):** nothing about forecasts is stored; the API fetches live Open-Meteo data and the forecast-change view comes from the Previous Runs API, so the storage estimate no longer applies.
- [x] **F2. Some forecast history may already be archived.** Open-Meteo has a "previous runs" API for regular (non-ensemble) models, which may cover part of what the doc plans to snapshot. Confirm what's covered and snapshot only what isn't. **Decision:** confirm which models and how far back Open-Meteo's archives can backfill; snapshot only what is not archived. **Action:** research still to do. **Outcome (closed Oct 7, 2026; checked with curl against the public APIs for Helena, Laramie and Loveland):** the Previous Runs API covers the deterministic GFS-based forecast for temperature and precipitation at day offsets 0 to 7 from about January 2024 with no gaps at the three stations, and precipitation probability from October 2024 (none for ECMWF); it does not cover ensemble runs, which is no longer needed because percentiles are used only in the live forecast chart and no percentile history is kept. Nothing is snapshotted. Details in proposal 06 and `docs/guides/02-api.md` section 5.6b.
- [x] **F3. AWN history depth is unknown and paging is slow.** Each call returns about one day of 5-minute data, limited to one call per second per key. Start the poller right away and run a one-off test per station to see how far back data goes. **Decision:** run a one-time backfill per station (can be run locally first). Every write must be idempotent (re-running inserts no duplicates and changes nothing).
- [x] **F4. Use ACIS to get PRISM data.** Downloading PRISM directly means processing map grid files. ACIS can return PRISM values for a point as plain JSON with one extra call. **Decision:** PRISM is deferred. Every station uses its nearest airport weather station as the baseline. **Action:** confirm the airport for Loveland, since the doc currently uses the Fort Collins volunteer station.
- [x] **F5. Reference stations may define "a day" differently.** Volunteer stations like Fort Collins often record the day ending at 7am or 5pm, not midnight, which skews GDD comparisons. Check each reference station's reading time and match it or label the bias. **Decision:** airport stations report midnight-to-midnight days in local standard time (no daylight-saving shift). Compute the backyard daily rollups used for baseline comparisons on the same local-standard-time days, and note the day definition on the chart.
- [x] **F6. Fix the rules for snow and counter resets.** Unheated gauges miss most snow, so October–April comparisons will be wrong, and AWN rain counters jump when a console reboots. Consider showing rain vs. baseline for April–October by default, and treat negative jumps as resets and cap impossible ones. **Decision:** rain is the primary view. Show rain vs. baseline for April–October by default, with winter months flagged; derive totals from counter changes, treat drops as resets, and cap impossible jumps.

## Cost

- [x] **C1. Pick a cost tier.** Rough monthly costs: free tiers everywhere ~$3–5 (fragile), realistic cloud (Fly + Supabase Pro) ~$30, or one small VPS running Docker Compose with cloud backups ~$5–7. The VPS option is cheapest and gives true local/production parity, but you lose managed database and auth. **Decision:** reviewed; keep the current plan (Netlify free, Fly about $3–5/mo, Supabase free). The single-server Docker Compose setup stays a fallback only; Hetzner US now starts around $20/mo and other 2 GB servers are $10–12/mo.
- [x] **C2. Supabase free tier is risky for production.** Free projects pause after about a week of inactivity, which would stop ingestion and cause permanent gaps, and they have no managed backups. Use Pro or self-hosted Postgres for production. **Decision:** reviewed; stay on the free plan. Supabase pauses only projects with little database activity, and the poller writes every 5 minutes. Upgrade to Pro if the database nears 500 MB or a pause warning arrives.
- [x] **C3. Connecting Fly to Supabase has a catch.** Supabase's direct connection is IPv6-only unless you pay ~$4/mo for IPv4, and its shared pooler (in one mode) breaks the Rust database library's query caching. Use the pooler's session mode or IPv6 direct, with both services in the same region. **Decision:** a deployment note for the API guide, with no design change. Connect from Fly using the direct (IPv6) connection or the pooler in session mode, never transaction mode, and put Fly and Supabase in the same region.
- [x] **C4. Normal storage growth is small.** Station observations are about 315,000 rows (60–120 MB) a year and reference data is a few MB. Forecast snapshots are the only real growth risk (F1). **Decision:** noted; no change.
- [x] **C5. Decide where backups run and live.** Scheduled GitHub Actions turn off after 60 days of repo inactivity. Run a nightly dump from the server to cheap cloud storage (pennies a year) with the same alerting as P4. **Decision:** a scheduled machine in its own Fly app (`famweather-backup`) runs once a day with its own backup-only database login, takes a `pg_dump`, encrypts it before upload, and stores it in AWS S3 (existing account). It pings the same alert service as the poller (P4), and the same container can run on demand locally. No GitHub Actions schedule is involved.
- [x] **C6. Netlify pricing and proxy traffic.** Netlify moved to credit-based pricing, and proxied API traffic counts against it. Small at this scale, but one more meter to watch, and it goes away under P1. **Decision:** reviewed; no change.

## Docker Compose (local and self-host parity)

- [x] **D1. Supabase doesn't fit cleanly in one compose file.** The Supabase CLI runs about 10 of its own containers outside your compose file. Instead, run plain Postgres plus Supabase's auth server and a local mail catcher for magic links in compose. **Decision:** compose runs plain Postgres, Supabase's auth server and a local mail catcher, alongside the Rust service and Caddy. **Revised Oct 7, 2026 (proposal 05):** login is email + password with hand-delivered set-password links, so no mail catcher is needed.
- [x] **D2. Local and cloud tokens are signed differently.** Hosted Supabase signs with public/private key pairs, while a local auth server defaults to a shared secret with well-known demo values. Make the token check configurable for both and ensure production can never load demo keys. **Decision:** the API's token check supports both signing methods through config, and production must refuse demo keys.
- [x] **D3. Add a local reverse proxy.** There is no local stand-in for Netlify's `/api/*` proxy. Add Caddy (or nginx) to serve the web app and forward `/api/*` to the API; the same config can run in production if you choose the VPS option. **Decision:** Caddy serves the static build and forwards `/api/*` to the API, mirroring Netlify (see P1, D4).
- [x] **D4. The SvelteKit adapter decides portability.** The Netlify adapter produces Netlify-only functions that won't run in a container. Use a static or Node adapter so one build runs locally and in the cloud. **Decision:** static adapter; the same build is served by Netlify in the cloud and by Caddy locally.
- [x] **D5. Pick one migration tool.** Supabase migrations and Rust's `sqlx` migrations would fight over the schema. Use one (likely `sqlx`) in a private schema and leave Supabase's auth tables alone. **Decision:** use `sqlx` migrations only, in the private app schema.
- [x] **D6. Make local runs safe and offline-capable.** A local poller using real family keys would compete with production for AWN's rate limit. Add a flag to turn polling off, a mode that replays recorded API responses, and keep secrets in a git-ignored `.env` with a committed `.env.example`. **Decision:** develop against the local Postgres in compose; never point local runs at production. Locally the poller is off by default and replays recorded responses, and real AWN calls use only your own station key. Backfills are tested locally, then the same job (safe to repeat) is run once against production from a one-off Fly machine, sharing the poller's lock and rate limit. The production poller starts early because station history cannot be rebuilt once it has aged out of Ambient's servers (revised Oct 7, 2026: forecast snapshots are no longer stored, so forecasts are no longer a reason).

## Gaps and contradictions in the doc

- [x] **G1.** The doc says the browser sends the token on every request but also considers a server-side cookie session (see S2). **Decision:** the browser sends the token on each request; no server-side cookie session (see S2).
- [x] **G2.** "Only the poller reads credentials" conflicts with a single binary running both API and poller (see S5). **Decision:** resolved by splitting the API and poller (see S5, P3).
- [x] **G3.** "Row-level security with no rules" vs. "a private schema" is left undecided (see S6). **Decision:** use a private schema (see S6).
- [x] **G4.** Who is the admin, who sends invites, who can run the `add-station` CLI, and who sets up the initial family follows? **Decision:** Rodney is the only admin and sends every invite; no one else has admin powers.
- [x] **G5.** How does the app's `users` table stay in sync with Supabase's own user list? **Decision:** no sync job. The admin invite command creates the Supabase login, the app `users` row (display name, active flag) and the starting family follows in one step. New users see an empty state until they add a station or a follow is approved.
- [x] **G6.** `application_key` is a per-credential column, but the limits describe one application key for the whole app. Which is it, and is it secret? **Decision:** one AWN application key for the whole app, stored as a Fly secret (used by the poller and the connect flow; a separate dev key in the local `.env`). Each station-owning user has one AWN API key, stored encrypted in `credentials`. Drop the per-credential `application_key` column.
- [x] **G7.** `forecast_snapshots.location_id` points at no table and has no access rule. **Decision:** add a `forecast_locations` table with one location per station (rounded coordinates); access to a location follows access to its station via `can_view`. *(Superseded by proposal 06: no forecast tables are built, so `forecast_locations` and `forecast_snapshots` do not exist.)*
- [x] **G8.** The "check AWN key" flow and the poller share the same 1-per-second limit on a key with no plan for coordinating them. **Decision:** the poller uses at most 2 of the application key's 3 requests per second, leaving room for the connect flow; both back off and retry when AWN says "too many requests".
