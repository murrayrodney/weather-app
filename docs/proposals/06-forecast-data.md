# Proposal 06: Where forecasts and forecast-change history come from

**Status:** Accepted by Rodney, Oct 7, 2026: option A (store nothing; the change view is day-by-day from the Previous Runs API). The verification items were run by an agent with curl on 2026-10-07 (results in "Verification results" below), not by Rodney; what curl cannot settle is recorded as accepted risk. Research date: 2026-10-07. Doc pages were read through a fetch tool that summarises them; the "tested" items below are live calls I made to the Open-Meteo APIs on 2026-10-07 (Helena coordinates, no API key). Anything I could not see is marked unverified.

## Plain-language summary

- Your new direction (show the forecast with percentile bands like a normal forecast site, do not archive percentiles) removes the main reason the poller stores forecasts.
- **Recommendation: store nothing (option A).** The forecast charts use live Open-Meteo data, fetched and cached by our API, with p10/p50/p90 bands computed from the ensemble members on request.
- The "how did the forecast change" view uses Open-Meteo's own archive: the Previous Runs API gives "what was forecast 1 to 7 days ahead" for the same hours, including precipitation and, for GFS, precipitation probability. A second archive, the Single Runs API, gives a specific past model run (data from April 2026, so about 6 months, tested working with no key; its free-use terms are not stated).
- Effect: the `forecast_snapshot` job, `forecast_runs`, `forecast_snapshots` and the `FORECAST_SNAPSHOT` health check go away (about 100 MB a year saved against the 500 MB budget). The poller no longer needs to go live early for forecasts; only for AWN data.
- Forecast-vs-gauge later is still possible: compare the archived forecast to the gauge at that time, with nothing stored now.
- Risk: we depend on Open-Meteo keeping those archives. Fallback (option B): a tiny deterministic-only snapshot, which can be added later without losing anything we would otherwise have kept.

## Problem

Design Doc and guides 03 (section 7.6), 04 (0008 `forecast_runs`, `forecast_snapshots`), 02 (section 5.6) and 01 (forecast-change page) assume the poller must record 6-hourly ensemble percentiles on every model run because "Open-Meteo does not archive ensemble runs" (Review Findings F1, F2; F2's research action is still open). Rodney's Oct 7 direction: percentiles are only for the forecast charts themselves, not for history; the history view shows how the forecast changed; nothing about percentiles is archived. That reopens F2 and the build-order rule "the production poller starts early because forecast snapshots cannot be backfilled" (Review Findings D6).

## Verified facts

From the docs pages and live calls on 2026-10-07.

1. **Previous Runs API** ([docs](https://open-meteo.com/en/docs/previous-runs-api)). Endpoint `https://previous-runs-api.open-meteo.com/v1/forecast`. Same models as the Forecast API. It returns fixed lead-time offsets, not whole runs: variables like `precipitation_previous_day1` ... `_previous_day7` (and Day 0 = the current run) give the value for each valid hour as forecast about N days earlier. Variables with these offsets include temperature, apparent temperature, humidity, dew point, precipitation, rain, showers, snowfall, weather code, pressure, cloud cover, 10 m wind speed and direction. **Precipitation probability is not listed in the docs**, but tested: `precipitation_probability_previous_day1` and `_day3` returned values for the default (best match) and `gfs_seamless`, and none (all null) for `ecmwf_ifs025`. Hourly resolution. Archive: most models from January 2024 (some later; GFS temperature from March 2021). Tested: `gfs_seamless` precipitation for 2024-02-01 and 2025-06-01 was fully populated; 2023-02-01 was empty. Ensemble models are not supported (only a "HGEFS ensemble mean" appears in the model list). The docs state no rate limit for this endpoint beyond the general terms (fact 6).
   - The offset is in whole days, not run numbers. So for a target day you get 7 earlier opinions about it, one per day-ahead, plus the current one. It does not say which model run each value came from (my reading; the docs describe offsets "rather than as a seamless time-series").
   - Tested with `forecast_days=16` and the default model: `precipitation_previous_day7` had values for 379 of 384 hours, so a day-7 offset is available across the whole 16-day window.
2. **Single Runs API** ([docs](https://open-meteo.com/en/docs/single-runs-api)). Endpoint `https://single-runs-api.open-meteo.com/v1/forecast`, same parameters as the Forecast API plus required `run=YYYY-MM-DDTHH:MM` (UTC init time, must be a valid cycle). Archive: ECMWF IFS HRES 9 km from 2024-03-14; most other models from 2026-04-02. Includes precipitation probability and all common hourly and daily variables. The docs page does not say whether it is free or commercial-only (it shows the same licence selector as the other APIs). Tested with no key: run `2026-10-06T00:00` and `2026-10-06T06:00` worked (default model, 16 days); `run=2026-05-01T00:00` with `gfs_seamless` worked (71 of 72 precipitation hours); `run=2026-03-01T00:00` with `gfs_seamless` returned HTTP 400 (before archive start); `ecmwf_ifs` for 2026-03-01 returned data. Response is slower than the live API (docs). No stated weighting or rate limit. **Not verified: that the free non-commercial licence covers it, and whether its coverage stays available.**
3. **Ensemble API** ([docs](https://open-meteo.com/en/docs/ensemble-api)). Endpoint `https://ensemble-api.open-meteo.com/v1/ensemble`, required `latitude`, `longitude`, `models`. Global models relevant here: NOAA GFS Ensemble 0.25 deg (`gfs025`, 31 members, 3-hourly interpolated to hourly, 10 days, every 6 h), GFS 0.5 deg (35 days), ECMWF IFS 0.25 deg (`ecmwf_ifs025`, 51 members, 15 days, every 6 h), ECMWF AIFS (51, 15 days), ICON global (40, 7.5 days, every 12 h), GEM (21, 16 days), UK MOGREPS-G (18, 8 days). European-only models do not cover Montana, Wyoming or Colorado. Variables include 2 m temperature, precipitation, rain, snowfall, wind speed and gusts at several heights, cloud cover, weather code, soil data, CAPE and more; **precipitation probability is not an ensemble variable** (it is derived from members). The API returns every member as its own series (`precipitation`, `precipitation_member01`...), not percentiles; docs point to a separate ensemble-mean API for means and spreads. Tested: `gfs025` for Helena returns members; `ecmwf_ifs025` for all three station locations in one request returned a 3-element array, each with 360 hourly steps and 51 series per variable (temperature and precipitation). Up to 3 past days are available. The docs' sample call "is equivalent to 4.0 calls": calls are weighted by variables, locations, days and models, so a 3-location, 2-variable, 15-day request counts for more than 1 (exact formula unverified).
4. **Forecast API** ([docs](https://open-meteo.com/en/docs)). Endpoint `https://api.open-meteo.com/v1/forecast`. Default "best match" model; selectable: GFS seamless (up to 16 days), HRRR (US), NBM (US), NAM (US), ECMWF IFS HRES 9 km and IFS 0.25 deg (15 days), GEM, ICON. Hourly: temperature, precipitation, precipitation probability (chance of more than 0.1 mm in the preceding hour; built from 30 ensemble members at about 27 km), wind, gusts, cloud, weather code and more. Daily: `temperature_2m_max/min`, `precipitation_sum`, `precipitation_probability_max`, `wind_speed_10m_max`, etc. `past_days` 0 to 92. So the site needs no stored data to draw ordinary hourly and daily forecasts; the ensemble API is only needed for the bands.
5. **Browser calls and CORS.** Tested: `api.open-meteo.com` answers with `access-control-allow-origin: *`, so a browser can call it directly. The terms page does not say whether direct browser use is allowed (unverified). Rate limits are enforced per caller (IP; my assumption, the docs do not say).
6. **Free tier and terms** ([pricing](https://open-meteo.com/en/pricing), [terms](https://open-meteo.com/en/terms)). Non-commercial only: 600 calls per minute, 5,000 per hour, 10,000 per day, 300,000 per month; no uptime guarantee; they "may block" misuse without notice. Data is CC BY 4.0, so credit is required (the guides already put it in the footer and on forecast charts). The terms list private or non-profit sites with no ads or subscriptions as non-commercial, which fits. No API key for the free tier (every call above worked without one).
7. **Existing design numbers.** 03 section 7.6 estimates about 0.5 M rows a year (3 locations, 2 models, about 60 windows, 4 runs a day), and 04 section 5.8 says about 100 MB a year with no pruning in v1. The job also polls metadata about 144 times a day.

## What each option means

Common to all options: the browser draws the normal forecast (hourly and daily, with bands) from live data and nothing about percentiles is stored. Percentiles (type-7 per hour or per window from the member series, as in the existing `core::forecast::aggregate`) are computed in our API, not the browser: 51 members x 15 days x variables is tens of thousands of numbers per location, and the API can return a compact `{time, p10, p50, p90}` shape. Via our API means one cache shared by the family and one egress IP for Open-Meteo to see.

### A. Store nothing

- **Forecast view:** new `GET /stations/{id}/forecast` (hourly and daily, deterministic plus ensemble bands). The API calls Forecast API and Ensemble API for the station's rounded coordinates, caches the result in memory for about 30 minutes (model runs change every 6 hours; a short TTL is safe), and returns it. Access check via `can_view` as every other route.
- **Change view:** new `GET /stations/{id}/forecast/changes?date=` (or a date range) calls the Previous Runs API for `precipitation_previous_day0..7` and, for the default/GFS model, `precipitation_probability_previous_day0..7` (and temperature if wanted). Result: for each day, the total and probability as forecast 0 to 7 days earlier. Cache 1 to 3 hours. Optional upgrade: the Single Runs API for exact runs in the last 6 months (see fact 2), if its terms are confirmed.
- **Poller:** remove the `forecast_snapshot` job, `forecast_models.toml`, metadata polling, `FORECAST_SNAPSHOT` health check, startup catch-up step and `job_runs` entries for it. `forecast_locations` stays only as a way to hold per-station rounded lat/lon (or move them onto `stations`; one decision for 04).
- **DB:** drop `forecast_runs` and `forecast_snapshots` (migration 0008) and their grants; no 100 MB a year growth; `DBSIZE` watching is simpler.
- **Web:** `ForecastHistoryChart` and `forecast.ts` change from "p50 per run" to "forecast at N days ahead" lines and a day-by-day table; a new hourly/daily forecast chart with percentile ribbons. `prob_precip` panel remains (from GFS previous-day values).
- **Tests and fixtures:** recorded Open-Meteo responses (forecast, ensemble, previous runs) as fixtures; API tests with a stubbed client; no DB seed data for snapshots. The poller's ensemble aggregate tests move to the API crate.
- **Open-Meteo load:** about 3 locations x (forecast + ensemble + previous runs) at a 30-minute cache is under about 500 calls a day even if every call weighed several units, well below 10,000 a day; the 600 per minute limit is only a concern on a cold cache after a deploy (add a small per-location request lock).
- **Build order:** no forecast data to protect. Early poller go-live is justified only by AWN ingest (the AWN history depth test, F3).
- **Forecast vs. gauge later:** possible. Previous Runs archives from January 2024, so comparing "forecast 1 day ahead" with gauge totals needs no stored forecast; it can even be backfilled for the past two years.
- **Weak points:** reliance on Open-Meteo's archive staying available and free; day-offset granularity (not model-run granularity); probability is GFS-derived and not available for ECMWF; model point is a grid cell, not the station (applies to all options).

### B. Small deterministic snapshot

- Keep a trimmed job: on each new model run (or four times a day on a timer, which drops metadata polling) store the deterministic best-match forecast for a few variables per location.
- **Storage estimate:** per location per run about 40 six-hour precipitation windows plus 10 daily highs and 10 daily lows, about 60 values; 3 locations x 4 runs x 365 days is about 0.26 M rows a year, roughly 25 to 40 MB with indexes (my estimate; the current design's 0.5 M rows for percentiles is the cross-check). A one-row-per-run array layout would be a few MB.
- Poller: keeps a `forecast_snapshot` job (simplified: no ensemble, no member count assertion) and a run table or one table; tests and fixtures for the job stay.
- API: `forecast/history` stays, now serving the DB; plus the live forecast endpoint from A.
- Build order: the early-go-live rationale still holds in a weaker form (history before go-live is lost, but Previous Runs would let you backfill 2024 onward, so even this rationale is weak).
- Forecast vs. gauge: straightforward, self-contained.

### C. Hybrid

- A for the change view (Previous Runs), plus a minimal snapshot only for what it cannot give: true per-run history beyond the Single Runs window, or variables with no previous-day values. In practice that is B-lite for precipitation only.
- Costs both code paths. Worth it only if the Previous Runs day-offset view proves too coarse once Rodney sees it, so I would treat C as the follow-up to A, not the starting point.

| | A. Store nothing | B. Deterministic snapshot | C. Hybrid |
|---|---|---|---|
| Poller job | removed | kept, simplified | kept, minimal |
| DB tables | `forecast_runs`, `forecast_snapshots` dropped | one slim table pair, about 25 to 40 MB a year (estimate) | slim, precipitation only |
| New API routes | live forecast, change view | live forecast, history | live forecast, change view, history |
| Granularity of "change" | day-ahead offsets 0 to 7 (per-run for last 6 months if Single Runs allowed) | every model run, from first poll | both |
| Depends on Open-Meteo archive | yes | no for change history; yes for live view | partly |
| Backfill possible | yes (from Jan 2024) | no | partly |
| Forecast vs. gauge | yes, from archive | yes, from own data | yes |
| Code and tests | least | medium | most |
| Early-poller-go-live reason | AWN only | partly still | partly still |

## Recommendation

**Adopt A: no forecast storage.** Live forecast and ensemble bands through our API (cached, percentiles computed server-side), and the change view from the Previous Runs API. It matches your direction, removes a job, two tables, a health check and a recurring storage cost, and keeps forecast-vs-gauge open. Present the change view first as "forecast N days ahead" for precipitation total, probability and high/low; Single Runs can later upgrade it to true per-run lines if its free-use terms are confirmed.

**Fallback:** if the pre-build check shows Previous Runs gaps at the stations, an unacceptable response time, or Open-Meteo terms that rule out our use, switch to B (a deterministic-only snapshot). Because B can be added later and A loses nothing, the choice is reversible, except that history that was never stored cannot be recovered after an archive disappears. If Rodney wants to hold that risk down cheaply, B's few-MB array layout is the insurance.

Browser-direct calls are not recommended: it bypasses the shared cache, needs `open-meteo.com` hosts in CSP `connect-src` (the guides allow only Supabase), spreads the rate limit across devices and exposes station coordinates to the browser's network log (they are rounded, but they are the access-controlled data in G7/S10). CORS is open, so it stays possible if the API becomes the bottleneck.

## Decisions made when applying option A to the guides (Oct 7, 2026)

- `forecast_locations` is dropped: the API uses each station's own rounded `stations.lat`/`lon` (04 section 5.5), after `can_view`.
- Deterministic series and the change view are pinned to `gfs_seamless` (best match returned identical values at all three stations, but may change model later). Ensemble bands use `ecmwf_ifs025` alone (51 members, 15 days); no merging across models.
- Forecast days are the station's local wall-clock days. Cache: 30 minutes for the forecast, 2 hours for the change view, stale-if-error, one upstream call per location under load (02 section 5.6).
- Migrations renumbered: 0008 `ops_tables`, 0009 `can_view` (no forecast migration). F2 and Q9 are closed.

## Verification results (run with curl by an agent, 2026-10-07; no API key)

Coordinates are the rounded station areas: Helena 46.6,-112.0; Laramie 41.3,-105.6; Loveland 40.4,-105.1. Open-Meteo snaps each to its own grid cell (returned: Helena 1195 m, Laramie 2178 m, Loveland 1531 m elevation). Responses are deflate-compressed; use `--compressed` (without it curl saved an empty body).

1. **Previous Runs, last 30 days plus next 7 (888 hours), best match, `gfs_seamless` and `ecmwf_ifs025`, all three areas.** `temperature_2m`, `precipitation` and their `_previous_day1/2/3/5/7` versions: 888 of 888 non-null for every combination. `precipitation_probability` and its `_previous_dayN` versions: 888 of 888 for best match and `gfs_seamless`; **all null for `ecmwf_ifs025` at every offset** (current-run probability is populated for ECMWF, previous-day is not). Payload about 11 to 12 KB compressed per call, 1.0 to 1.6 s.
2. **Archive depth.** `gfs_seamless` precipitation and temperature at day-1 and day-7 offsets start about 2024-01-19 (day 1) and 2024-01-25 (day 7), then are complete (no nulls over 2024-08-01 to 2025-03-01). **Probability starts 2024-10-11** (day 1; the day-7 offset from about 2024-10-18); earlier months are all null. From 2024-10-15 to 2026-10-06 (17,328 hours) at all three areas: zero nulls for temperature and precipitation at day 1 and day 7 and for day-1 probability; day-7 probability had 64 null hours (2024-10-15 to 2024-10-17 only). So no gaps for the stations, only the start dates above.
3. **Best match equals `gfs_seamless` here.** For all three areas over the last 37 days, best match and `gfs_seamless` returned identical values for every variable and offset. Best match may change model in future, so the guides pin `models=gfs_seamless` for the change view.
4. **Daily variables are not offered for previous runs** (`precipitation_sum_previous_day1` is rejected with HTTP 400). The API aggregates the hourly series into local days itself.
5. **Size and latency of a long history.** A two-year hourly request (6 variables, one location) is about 745 KB decoded and took 7 to 12 s. A 30-day window is a few KB and about 1 s. The change view therefore requests at most a 14 to 30 day window per call and does not fetch years at once.
6. **Ensemble, three locations in one request.** `ecmwf_ifs025`, 15 days, temperature and precipitation: 3 locations, 360 hourly steps, 51 series per variable (control plus 50 members), about 567 KB decoded, 2.3 s. `gfs025`, 10 days: 31 series per variable, 241 KB, 1.7 s. `ecmwf_aifs025` (51 members, 15 days) 567 KB, 1.8 s. `gem_global` (21, 16 days) 260 KB, 1.6 s. `icon_seamless` (40, 7 days) 218 KB, 1.5 s. Both ECMWF and GFS in one call: 80 members per variable, 923 KB, 2.0 s. The last few hours of each series are null for every member (ECMWF and AIFS up to 9 hours, GFS up to 5; the same hours for all members of a variable); the percentile code must skip nulls and omit a time step when fewer than 5 members have a value. Ensemble grid cells are snapped to 0.25 degrees (Helena 46.5,-112.0; Laramie 41.25,-105.5; Loveland 40.5,-105.0). The guides use `ecmwf_ifs025` for 15-day bands and `gfs025` for the first 10 days when a probability-of-precip band is wanted; bands are drawn from one model per chart, not a merge.
7. **Forecast API.** 16 days of hourly temperature, precipitation and precipitation probability plus daily max/min/sum/probability-max: 384 of 384 hours and 16 of 16 days non-null, about 2.2 KB compressed, 0.4 s, identical for best match and `gfs_seamless`.
8. **Single Runs.** `gfs_seamless` runs 2026-04-02T00:00 (the first archive day), 2026-06-15T12:00 and 2026-10-05T06:00 at all three areas: 240 of 240 temperature hours and 239 of 240 precipitation and probability hours, 0.8 to 1.1 s each. The pricing page's plan table shows Single Runs as included in the free column (the table has no column labels in the fetched text, so this is my reading) and the Single Runs page offers a "Non-Commercial" usage licence option. Treated as available but optional; the first version does not depend on it.
9. **Call weight.** The pricing page's FAQ says one call is one request for at most 10 variables and at most 2 weeks for one location; larger requests count fractionally (2 weeks with 15 variables is 1.5 calls, 4 weeks is 3.0). So a 30-day, 6-variable previous-runs call is about 2.1 to 2.6 calls and a 3-location 15-day ensemble call about 3 to 4. With a 30-minute cache that is well under 1,000 weighted calls a day (limit 10,000 a day, 600 a minute).
10. **Rate-limit headers.** None returned (no `x-` or `ratelimit` headers), so the guides do not rely on them; handle HTTP 429 with backoff.

**Accepted risks (not checkable with curl, not assigned to anyone):** (a) licence wording: the terms page lists private sites or apps without subscriptions or advertising as non-commercial and requires CC BY 4.0 credit (footer and chart captions already do this); direct browser use is not addressed, which is moot because the browser never calls Open-Meteo; (b) long-term availability and continued free access of the Previous Runs, Single Runs and Ensemble archives and the per-IP behaviour of the 10,000-a-day limit; (c) which model run each previous-day value comes from is not documented (day offsets, not run numbers); (d) the 50-member API response sizes could grow if Open-Meteo adds members. If any of these changes, the fallback is option B.
